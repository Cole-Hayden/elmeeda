# Spec Delta

## Purpose

Lets API clients create issues and relies on durable storage to keep them. An issue has a unique identifier and the breakdown details known so far.

## ADDED Requirements

### Requirement: Create an issue
The system SHALL expose `POST /issues`, which needs no request body, creates one issue, and responds with status 201 and a JSON object containing the issue's `issueId`.

#### Scenario: Issue is created
- **WHEN** a client sends `POST /issues` with no request body
- **THEN** the response status is 201
- **AND** the response body is a JSON object whose only field is `issueId`, holding a UUID

### Requirement: Create an issue with breakdown details
`POST /issues` SHALL accept an optional JSON body with any of `truckUnitNumber`, `problem`, `location` (`description`, `latitude`, `longitude`), `drivable`, `neededBy`, `maxDistanceMiles`, and `maxBudget`, and SHALL store every detail it receives with the issue.

#### Scenario: Details are stored
- **WHEN** a client sends `POST /issues` with valid details
- **THEN** the response status is 201
- **AND** the response body is a JSON object whose only field is `issueId`
- **AND** the stored issue holds those details

#### Scenario: Only some details are known
- **WHEN** a client sends `POST /issues` with only some details
- **THEN** the response status is 201
- **AND** the details that were not sent remain unset on the stored issue

#### Scenario: Truck does not exist
- **WHEN** a client sends a `truckUnitNumber` that matches no truck
- **THEN** the response status is 422
- **AND** no issue is stored

#### Scenario: Details are invalid
- **WHEN** a client sends a detail that fails validation, such as an unknown `problem` or a negative `maxBudget`
- **THEN** the response status is 422
- **AND** no issue is stored

### Requirement: Server assigns the issue identifier
The system SHALL generate each `issueId` itself, and each created issue SHALL receive a distinct identifier.

#### Scenario: Each request creates a distinct issue
- **WHEN** a client sends `POST /issues` twice
- **THEN** the two responses contain different `issueId` values

#### Scenario: Client-supplied identifier is ignored
- **WHEN** a client sends `POST /issues` with a JSON body containing an `issueId`
- **THEN** the response status is 201
- **AND** the returned `issueId` is generated by the server, not the supplied value

### Requirement: Created issues are stored durably
The system SHALL save an issue to the database before reporting that it was created.

#### Scenario: Created issue exists in the database
- **WHEN** `POST /issues` responds with status 201
- **THEN** the database contains exactly one issue with the returned `issueId`

### Requirement: Storage failures are reported safely
The system SHALL respond with status 503 when the issue cannot be saved because storage is unavailable, and the response SHALL NOT expose internal details.

#### Scenario: Database is unavailable
- **WHEN** a client sends `POST /issues` while the database cannot be reached
- **THEN** the response status is 503
- **AND** the response body contains a generic error message without connection details
